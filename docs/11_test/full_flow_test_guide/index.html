2平台与模块

HuntAI Test 是企业内部自用的 AI 测试平台：编排接口 / Web / 性能自动化，用 AI 生成与分诊，用确定性工作流、副作用分级、审批与证据链约束副作用，并与 Jira / GitHub / CI / Release 打通。平台编排质量证据，不替代外部系统。

2.1 北极星闭环

导入 → 生成 → 评审 → 执行 → 归一化 → 分诊 → 门禁 → 缺陷/Release → 证据/审计 这条链路由后端状态机裁决；前端只展示、发命令、GET 对账；AI 只做理解/生成/聚类/解释，不决定权限、审批、重试、门禁或外部写。

3.5 关键架构约束

控制面权威

TestRun、ApprovalRequest、ExecutionEnvironment、ReleaseTask、GateEvaluation 的状态只由后端域命令迁移；前端、SSE、Worker、工作流引擎和外部系统只能提供请求、提示或观察。

执行隔离

浏览器执行、压测、大报告解析、AI 调用都在隔离 Worker / 子进程；API 进程不被长任务拖垮。M0–M3 用进程内子进程 + 数据库状态实现，不启用 Temporal。

副作用可证明

每次外部写可追溯 tenant、actor、参数哈希、审批、外部请求 ID、结果与证据；幂等键 + CAS + 行锁保证重启/重试不重复副作用。

AI 受限

AI 只做理解、生成、聚类、解释与候选动作；权限、重试、幂等、审批、门禁、状态机由确定性平台控制。Agent 结果不进门禁。

  2. 确认当前用户能建库

9.4 执行编排（P08 / P09 / P14 / P16）

目标

发起一次真实 TestRun，观察 10 态流转、受理回执、结果归一化、取消与 SSE 对账；了解 Web / 性能 / Agent 的差异。

操作 A · 接口执行（最短闭环）

  1. P08 发起
    选择项目 → 执行来源 script → 选择刚批准的 ACTIVE 环境和 ACTIVE 接口用例 → 参数填 TARGET_ENV（可填 http://127.0.0.1:8190）→ 发起。
  2. 看受理回执
    返回 receipt.status=accepted；这只是受理，不等于完成。
  3. P09 看流转
    状态通常 PENDING → VALIDATING → RUNNING → SUCCEEDED；失败也可能 FAILED，这是有效结果。
  4. 看结果
    用例结果表出现 CaseResult；点进 StepRun 看断言与归一化摘要。

操作 B · 取消

  • PENDING / WAITING_APPROVAL / WAITING_EXTERNAL 取消 → 立刻 CANCELLED。
  • RUNNING 取消 → STOPPING；执行器收到停止信号后收敛，最终 CANCELLED。
  • 终态不可再取消；取消后仍可追加迟到结果/证据，但不得重开 run。

操作 C · SSE 与 GET 对账

P09 的进度通过 /api/v1/test-runs/{id}/events 推送；SSE 只展示，断线/重连后必须 GET /api/v1/test-runs/{id} 对账。SSE 与 GET 冲突时以 GET 为准。

操作 D · Web 执行

需要 Playwright Chromium：

cd backend
uv run playwright install chromium

创建 Web 用例（步骤含 goto / click / 断言），选择 platform_executor 环境执行；成功后 P13/P09 可看截图、视频、Trace。Playwright 是独立子进程，不阻塞 API。

操作 E · 性能执行

P16 选择性能用例；参数需要 TARGET_ENV、perf_whitelist、perf_scenario（如 users / run_time_seconds）。白名单外目标会 HT-POL-002 拒绝且不建审批；高风险压测需要审批；全局并发受配额与场景互斥约束。结果包含 p95 / 错误率，并进入同一套门禁对象。

压测只打自己的环境 不要用公网目标练手。白名单是硬约束；未声明或不在白名单的目标默认 DENY。

操作 F · Agent 试点

P14 可发起 Agent 任务并观察轨迹；Agent 结果不进入质量门禁，也不能作为发布证据。轨迹需要人工固化为 Script 资产并跑确定性 run 后才恢复门禁资格。终止信号会持久化。

对应 API

API-060–066（列表/详情/发起/取消/结果/步骤）、API-069/071/080（执行选项/命令回执/ApiToken 发起）、API-210（SSE）、API-220/221（制品）。

验收标准

  • 发起返回 accepted，但状态不是立刻终态。
  • 终态只能由后端迁移；刷新页面不会“猜”状态。
  • 每次运行都有 CaseResult；失败也有。
  • 取消后不会出现永久 STOPPING（心跳超时收敛）。

9.6 审批与 Policy Gate（P10）

目标

理解 L0–L4、Preview、九要素、四眼、param_hash、TTL、行锁单次消费；亲手体验“发起人不能批准自己”。

操作

  1. 触发一个 L2 动作
    注册执行环境（§9.3）、Jira 写缺陷（§9.8）或 Release prepare（§9.9）都会生成 ApprovalRequest。
  2. 看九要素
    P10 卡片自上而下六区 + 操作区；确认 tenant、actor、动作、目标、参数哈希、风险等级、候选审批人、TTL、证据。
  3. 自批被拒
    owner 打开自己发起的审批并点批准 → 403 HT-IAM-002。
  4. 换 admin 批准
    admin 批准 → APPROVED → 消费 → EXECUTED，并记录 execution_result=ok/failed/unknown。
  5. 拒绝与重提
    admin 拒绝并填原因 → REJECTED；owner 修改参数后重提，生成新请求、新 TTL、新哈希。

关键语义

场景行为
审批过期ApprovalRequest EXPIRED；关联 TestRun 保持 WAITING_APPROVAL，不自动放行、不自动取消
参数被改param_hash 不匹配，旧批准失效，fail-close
重复消费行锁 + execution intent，只有一次外部效果；重复请求返回同一执行引用
结果未知EXECUTED + execution_result=unknown；先按 external_request_id 对账，不盲重试
L3+再认证窗口不足时先 step-up（API-004），不能绕过审批

对应 API

API-110/111/121（列表/详情/候选）、API-112/113（决策/重提）、API-120（Preview）、API-004（再认证）。

验收标准

  • 发起人自批 100% 拒绝；admin 批准后 EXECUTED 且有 execution_result。
  • 参数/目标/权限变化后旧批准不能复用。
  • 审批过期不会把 TestRun 自动变成 CANCELLED 或 SUCCEEDED。

9.7 质量门禁（P11 / P12）

目标

创建版本化策略，观察 run 终态后异步生成不可变 GateEvaluation；理解 blocking 与 report_only 的差异。

操作

  1. P11 填 projectId
    粘贴 00000000-0000-4000-8000-000000000003；不填则页面不会出现创建卡片。
  2. 创建策略
    第一次建议 report_only，阈值 95 / 500 / 1；想体验阻断再切 blocking，需要显式二次确认。
  3. 跑一次执行
    按 §9.4 发起；终态后到 P12 看评估记录。
  4. 验证不可变
    修改策略后，历史评估不变；重评估会新建记录。
  5. 失败门禁
    用 Jenkins full-flow-fail 或失败用例；blocking + min_pass_rate=100 时评估为 fail。

关键语义

  • 只有 script/external_ci 且 TestRun 为 SUCCEEDED/FAILED、结果完整、策略可评估时才生成 pass/fail。
  • agent 永不生成 GateEvaluation。
  • CANCELLED / TIMEOUT、报告 partial、阈值缺配不得默认 pass；当前用“无评估 + 明确 reason”表达不可评估。
  • Check Run 同步失败不回滚门禁事实。

对应 API

API-140–143（策略 CRUD）、API-144–146（评估/历史/投影）。

验收标准

  • 评估记录含 policy_snapshot 与三阈值明细。
  • 历史记录不可变；策略更新不重写历史。
  • 缺配/partial/CANCELLED/TIMEOUT 没有 pass。
